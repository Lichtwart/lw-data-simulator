Firmware facts: see `firmware-core-v2.md` (cited as FW). The prototype is a single static page plus a tiny proxy; there is no build step (`README.md:7`).

## 1. Behaviour of the prototype

### 1.1 Counts
- **135 items in 46 groups** (script-evaluated from `GROUPS`, `index.html:191-272`): 55 `num` (sliders / manual number), 64 `alarm`, 10 `bin` (0/1 switch), 6 `mode` (AC mode). Per location: Outside, Building, Technical Room (`LOCS`, `:176`); per category: Lighting, Air Conditioning, EV Charger, Energy Meters, Kitchen & Service, Occupancy, Sensors, Fuses & Safety (`CATS`, `:177-180`).
- Item shapes (`:184-189`): `pct(name)` = slider 0..100 `%` step 5 default 50; `alarm(name,label,sev='MAJOR')`; `bin`; `num(name,label,{min,max,step,unit,def,manual?,alt?})`; `light(title,loc,base,alarmName)` = group with `<base>_brightness` + alarm. `manual: true` = slider **and** a number input (`<input type="number" min="0" step="any">`, `index.html:469-473`): the slider keeps the item's own `min/max/step`, the number input accepts any value >= 0 (used for lx and kWh values). Slider ranges of the three manual item families: `outside_brightness` 0..40000 step 250 (`:195`), `energy_total` 100..10000 step 50 (`:259`), `*_energy_value` 1..30 step 1 (`:267`). Re-checked: every `num` item and every `pct` item defines `min`, `max` and `step` (all 9 `num(...)` call sites and `pct`), so every numeric item has a slider range. `alt: 'C'` shows a °C hint next to a °F slider (`:418`, only UI, the sent value stays °F).
- Lights are 14 brightness items (all `%`, 0..100, step 5, def 50), 13 of them have a light alarm (Restroom has none, `:242-244`).

### 1.2 What is sent to Cumulocity (non-native names)
- **Measurement** `POST /measurement/measurements`, content type `application/vnd.com.nsn.cumulocity.measurement+json`: `{ source:{id}, time: ISO now, type: <item name>, <item name>: { value: { value: <n>, unit: <unit> } } }`, i.e. fragment = item name, series always `value` (`SERIES`, `:174`; `measurementBody`, `:335-338`). `unit` is `''` for `bin` and `mode`. `bin` value 0/1; `mode` value = index in `['heating','auto','cooling','dry','humidification']` = codes 0-4 (`AC_MODES`, `:182`; `measuredValue`, `:339-342`).
- **Send all values** (`:368-372`) = one `POST /measurement/measurements` with content type `...measurementCollection+json` and body `{measurements:[...]}` for every non-alarm item (71 measurements). Button **Send all values**; optional **repeat every N s** checkbox (default 30 s, min 5 s, `index.html:145`; `setInterval`, only while logged in, `:608-616`). Slider: value sent on `change` (release), switch: immediately, mode: on click (`:517-565`).
- **AC mode** is a multi-effect item (`sendMode`, `:350-357`, `Promise.all`): (1) measurement with the code; (2) event `POST /event/events` `{source,time,type:<item name>,text:"<Title>: <mode>",mode:"<mode>"}`; (3) device property `PUT /inventory/managedObjects/<deviceId>` `{ "<item name>": "<mode>" }` (content type managedObject). README says the same (`README.md:59`).
  - **Accepted break:** the event `type` and the inventory property name are both the item name (`index.html:352-356`). Renaming the AC-mode item id to the short library id (e.g. `ac_kitchen_mode` -> `ac_kit_mode`) therefore also changes the multi-effect event type and the inventory property name, not only the measurement. Existing consumers of the old event type/property will break; this is accepted together with the other non-native renames.
- **Alarm fire** (`fireAlarm`, `:361-366`): `POST /alarm/alarms` `{source,time,type:<item name>,severity:<chosen>,text:"<Title> active"}` where `title()` (`:274`) splits the id at `_`, capitalises each word and turns `co2` into `CO₂`, e.g. `ac_kitchen_alarm` -> text `Ac Kitchen Alarm active`. Severity default per item (MAJOR; fuses and CO2 leakage CRITICAL, `:252-256`), selectable CRITICAL/MAJOR/MINOR/WARNING (`SEVERITIES`, `:181`), remembered per item. Fire button locks for 3 s (`FIRE_LOCK_MS`, `:359`). Each fire raises a new alarm (no dedup logic in the page; Cumulocity dedups by type+source while active).
- **Clear all alarms** (`:374-380`, double click within 3 s): two requests `PUT /alarm/alarms?source=<id>&status=ACTIVE` and `...status=ACKNOWLEDGED` with `{status:"CLEARED"}`.
- Units: temperatures in **°F** (`:209-210,224-225`), energy `kWh`, current `A`, light `lx`/`%`. No generators, scenarios, presets or auto-fault logic exist in the prototype (grep for scenario/preset: none; the only "automation" is the repeat timer which re-sends the stored slider values unchanged).
- Persistence: browser `localStorage` keys `sim.view`, `sim.values`, `sim.sev`, `sim.login` (url, device id, user); the password only in `sessionStorage` (`sim.pass`) (`:281-298,622-625,660,677-680`). A stored value outside the slider range falls back to the default (`:295`).
- UI: two views (by location / by category), word-AND search over section, group, id and label (`:433-446`, `/` focuses, `Esc` clears), activity log of up to 300 entries (`:401-411`), dark/light via CSS.

### 1.3 Auth / proxy approach
- Login form: tenant URL (default `https://test.ram.m2m.telekom.com`), device ID (default `5111860056`), user, password (`:171,149-158`). Tenant URL is reduced to `https://host` (`tenantOrigin`, `:628-631`). On a foreign tenant domain the user is entered as `tenantId/user` (`README.md:35`).
- Auth = **Basic** `Authorization: Basic base64(user:pass)` plus header `UseXBasic: true` and `Accept: application/json` (`:314-324,636`). Login test = `GET /user/currentUser` then `GET /inventory/managedObjects/<deviceId>` (`:638-639`). Matches PRD §5.
- `server.js` (Node >=22.15, `--use-system-ca`): serves `index.html` on `127.0.0.1:8080` and forwards `/c8y/*` to the tenant given in header `X-C8Y-Tenant` (must match `^https://[a-z0-9.-]+(:\d+)?$`, `server.js:26-32`), forwarding only headers `authorization, content-type, accept, usexbasic` (`:13`), no redirect following (`:44`), logs `status METHOD URL` and the first 300 chars of any >=400 body (`:47-48`). Purpose: avoid CORS (`README.md:25-30`). Replaced in the new app by Rust-side HTTP (PRD §4).
- The prototype uses plain REST JSON (not SmartREST), no realtime/operations handling at all, and a **single hard-coded device**.

## 2. Mapping to the PRD library

Rules applied (PRD §17 plus findings):
- Lights -> native DALI lamps `light-1..light-14`; their 13 alarms -> native `lw_lampFailure_1_NN_generic` (302 MAJOR matches the prototype severity MAJOR; FW `firmware-core-v2.md` section 2). Outside brightness -> native `LW Dali Brightness`/`Lux1` plus native `lw_brightness_1_01_lost`.
- **The 10 `bin` items become the 10 native digital inputs** of the firmware (`NO_DIN` = 10) - decided 2026-10-12 (`docs/DECISIONS.md` D3; they are real on/off sensors: occupancy, EV slot occupied, water leakage), not Modbus registers. This leaves no spare DI for other demos on the same device. Series names are the native `Value01`..`Value10`; the human title is stored in `lw_configDigitalInputs[].title` (D1).
- Remaining numbers/modes -> Modbus registers; units converted to metric (PRD §11.3) so ranges change (see table). Writable registers (AC setpoint, AC mode) are floorplan targets (`writeRegisters`, plugin only accepts integers 0-65535 for `lw_modbusWrite`, see floorplan-plugin.md section 5); so setpoint = integer °C, step 1.
- **Slaves**: PRD §17 says "Modbus registers on slaves per prototype group", but the prototype has 46 groups and the firmware allows 20 slaves; moreover only groups with a measurement can have registers (a slave needs >=1 register, FW section 5.5). I therefore propose **13 slaves** (table below), merging energy meters.
- **Custom alarms (resolved 2026-10-12, DECISIONS.md D2)**: the prototype has **64 alarms**: 14 map to native DALI alarms (above), 22 attach to slaves (some slaves need 2 or 5 alarms) and **28 have no register at all** (kitchen equipment, order panels, 18 fuses, CO2 leakage, dry-room leak alarm). A slave therefore carries `alarms[]`, and a device-level item kind `customAlarm` covers alarms without a register/slave.
  - **Custom alarm type rule:** slave alarm = `lw_demo_<id:02>_<name>` (`id` = assigned slave id, `name` = alarm name = item id of the alarm, e.g. `lw_demo_19_en_frz_alarm`); device-level alarm = `lw_demo_<name>` (e.g. `lw_demo_co2_leakage`). A device-level `name` must not start with two digits plus `_` so the two forms cannot collide. Alarm types are written literally into floorplan `alarmTypes` (the plugin never suggests custom types, floorplan-plugin.md section 3.4).
- AC mode: 6 items, register `ac_<z>_mode` + event + device property (PRD §8 multi-effect). The prototype codes (0 heating, 1 auto, 2 cooling, 3 dry, 4 humidification) differ from the plugin's example multi options (0 Off, 1 Cooling, 2 Heating, 3 Automatic, `davaco-demo src/app/floorplan/model/fixtures.ts:329-332`); options are user-defined per widget, so keep the prototype codes in the library floorplan.
- Items ids <= 19 chars `[A-Za-z0-9_-]`: the prototype ids are up to 40 chars (e.g. `crew_manager_support_energy_peak_current`), so **all non-native ids are shortened** (script check: no duplicates, all <= 19; native alarm identifiers like `lw_lampFailure_1_01_generic` are firmware names, not library ids).
- Slave names <= 19 chars (longest: `Klima Trockenlager`, 18).

## 3. Tags and demo-client fit

- Prototype client "davaco": the items describe a **drive-through quick-service restaurant** (fry/flurry station, grills, presenters, order panels, drive panel, totem, EV chargers, dry storage, freezer/cooler, `davaco-demo` fixtures call it "Restaurant: kitchen, dining and storage", `fixtures.ts` `groundFloor.description`). Neither `gas-station` nor `retail` fits the kitchen part, so the third client tag **`restaurant`** (QSR) is added for kitchen/dining items (decided 2026-10-12, DECISIONS.md D4: the library ships the demos `gas-station`, `retail` and `restaurant`).
- Reasoning for the other items: `retail` = shop-floor basics that any store has (general lighting, AC, freezer/cooler, restrooms, dry storage, energy meters, fuses, water leakage, CO2 tank); `gas-station` = the same shop-side items plus forecourt-like items (outside totem, entrance lettering and signage, EV charging, outside brightness, canopy-like outside lights) because PRD's gas-station demo already uses cooling, EV charging and outside lighting (PRD §6.1 example, §7.4 `Ladesaeule 1`, `Kuehlung`). Items tagged `restaurant` only: fry/flurry/grill/presenter/order-panel alarms, dining and kitchen/scullery lights, dining and kitchen AC, dining/order/drive-panel energy, and the six fuse alarms `kitchen`, `dining`, `scullery`, `presenters`, `order`, `drive` (table rows 80, 81, 84, 85, 94, 95).
- Concretely: a `restaurant` demo = items carrying `restaurant` (83 of 135; this is the davaco demo), a `gas-station` demo = items carrying `gas-station` (93 of 135), a `retail` demo = items carrying `retail` (93 of 135). Counts re-verified against the table below. The `Tags` column above is the output of exactly these rules (regex rules in my generator: kitchen/dining/order/presenter/grill/fry/flurry/scullery/drive-panel -> restaurant only, **including the fuse alarms whose name contains one of these words** (kitchen, dining, scullery, presenters, order, drive); totem/entrance/outside/crew/manager/support/CO2/leakage/energy_total and the remaining fuse alarms (co2, parking, vestibules, restroom, dry_storage, freezer, cooler, crew, manager, support, totem, signages) -> all three; everything else retail + gas-station). They are suggestions; no source in the repos defines these tags (PRD only names examples).
- PRD §11.3 demo shape: `daliLampCount 14`, 5 DALI groups, 10 `digitalInputs`, 13 slaves, `sendIntervalSec 30` (prototype repeat default 30 s / min 5 s, `index.html:145`).

## 4. Scenarios / presets, generators, send interval logic (summary)
- Scenarios/presets: **none in the prototype**. PRD §8 scenarios are new; suggested first ones from the prototype's domain: `night` (lights off, EV slots free), `rush` (all slots occupied, high currents), `fault-freezer` (freezer_temp above -12 °C + alarm).
- Generators: **none** (values only change by manual slider/switch).
- Send logic: change-driven single POST + manual "send all" + optional timer re-sending the stored values every N s; PRD §8 adds generators and batching.
- Defaults to carry over: lights 50 %, setpoint 70 °F (-> 21 °C), actual 72 °F (-> 22 °C), AC mode `auto`, freezer 0 °F (-> -18 °C), cooler 38 °F (-> 3 °C), outside brightness 12000 lx, energy_total 1000 kWh, meter energy 1 kWh, peak 16 A / total 50 A.

## 5. Facts that conflict with or extend the PRD (short)
1. PRD §17 "135 items -> native" works for lights/brightness/DI; the 64 custom alarms needed `alarms[]` per slave plus device-level custom alarms (resolved, D2, section 2).
2. Prototype ids (up to 40 chars) violate the 19-char id rule -> renaming required (all done in the table).
3. Prototype uses `°F`; PRD wants metric -> ranges converted; the plugin demo and client tenant dashboards built on `<name>.value` will break (PRD accepts this).
4. Digital input titles in series names (old PRD §7.3) were not real firmware behaviour; resolved by D1 (native `ValueNN`, title in config).
5. The prototype never handled operations; the new app must (PRD §9). Floorplan control needs `lw_modbusWrite` to answer within 10 s (floorplan-plugin.md section 5).
